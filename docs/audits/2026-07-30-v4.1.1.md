# 稽核紀錄：v4.1.1（2026-07-30）

這一版全部來自 **v4.1.0 發版後的最終驗收稽核**（`@codex` xhigh，唯讀 + 實跑）。
它抓到一個我在 v4.1.0 自己引入的回歸，以及突變測試工具本身的假綠燈。

## 1. 回歸：讀取端的錯誤分類擴大時，把寫入端一起帶壞了（CRITICAL）

v4.1.0 把 `isMissingError()` 從 `{ENOENT, ENOTDIR}` 擴大成
`{ENOENT, ENOTDIR, EISDIR, ELOOP, ENAMETOOLONG}` —— 對**讀取端**是對的
（結構性錯誤不會自己好，該退回內建值）。

但 `readRawConfig()`（**寫入端**的基底）也在用同一個判斷，於是
「路徑上有東西、只是我讀不到」被當成「檔案不存在」→ 回空基底 →
`set_config` 會拿空基底套上變更寫回去，正好違反 v4.1.0 自己承諾的
「只有檔案不存在才用空基底」。

**修法**：寫入端改成只認 `ENOENT`，其餘一律拒絕寫入。兩端的判準必須分開 ——
讀取端問「這次讀不到要用什麼值」，寫入端問「覆蓋下去會不會弄丟還在的東西」。

新增三條斷言（`EISDIR` / `ELOOP` / `ENAMETOOLONG` 各一）與一個對應突變守住它。

## 2. 突變測試工具自己的假綠燈（MAJOR）

- `run(args)` 只接受一個參數陣列，收尾卻寫成 `run('git', ['status','--short'])`
  → 第二個參數被丟掉、**git 根本沒執行**，然後把空字串印成「worktree 乾淨」。
  實際上那時 worktree 有四個 modified files。
- 成因：還原時寫回的是 **LF 正規化後**的內容（比對片段是 LF，worktree 是 CRLF），
  整個 worktree 因 EOL 變更而變髒 —— 而唯一會發現這件事的檢查剛好沒在跑。

**修法**：分出 `exec(cmd,args)` 與 `run(args)`；還原寫回**原始 bytes**；
收尾與開跑時的 `git status` 比對（不是「必須是空的」，因為 worktree 可能刻意帶著待驗證的改動），
不一致就讓整支腳本以非零碼收場。

## 3. 突變覆蓋缺口（稽核指出，已補）

新增 5 個突變（14 → 19），補上：寫入端錯誤分類、根節點陣列、
`aliasReasoningEffort` 陣列、`ELOOP`、`getModelsPayload(snapshot)` 不重讀。

補的過程中，突變測試又抓出**兩條原本不夠力的斷言**：

- 「根節點是陣列時整份忽略」：陣列本來就取不到欄位，擋不擋都回內建值 ——
  斷言分辨不出來。改成驗 `userConfig.status.state === 'error'`（有擋才會是 parse 錯誤）。
- 「結構性讀檔失敗退回內建值」的三個 code 寫成一個迴圈：
  第一個 code 走結構性分支時會**清掉快取**，後面的 code 就算被錯分成「暫時性」，
  也會因為沒有 last-good 可用而一樣回內建值。改成每輪先重新建立 last-good。

## 4. 稽核指出、已更正的不實敘述

- 「把**每個**修補逐一改壞」→ 實際只涵蓋產品端；測試基礎設施的修補沒有突變覆蓋。已改寫。
- CHANGELOG 的「API 變更**皆**向後相容」→ `updateUserConfig()` 回傳型別由 `UserConfig`
  改成 `ConfigSnapshot`，舊呼叫端若直接取 `.aliasModel` 會壞。已改為明確標示這一項不相容。

## 5. 其他一併修掉的

  改為同時檢查 `status` / `exitCode` / 是否真的回 `PONG`。
- `verify-direct-api.mjs` 的暫存目錄清理只在成功路徑 → assertion 中途拋錯仍會留垃圾。
  改掛 `process.on('exit')`。

  修掉寫入端判準之後這條路徑已經是「拒絕寫入」，不再需要靠 rename 失敗兜底。

## 8. 環境事故（記錄，非程式碼問題）

清理突變測試用的 git worktree 時，`Remove-Item -Recurse` 跟著 `node_modules` 的
NTFS junction 走進去，把主 repo 的 `node_modules/.bin` 刪掉了，`npm run build` 因此找不到 `tsc`。
以 `npm install` 復原，`package-lock.json` 未變動。

**教訓**：刪含 junction 的目錄，要先確認 junction 已經拆掉（`(Get-Item x).Delete()` 之後
再 `Test-Path` 確認），或直接用 `cmd /c rmdir`（不會遞迴進 reparse point）。
